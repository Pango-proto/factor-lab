项目结构与版本控制范围
======================

整理原则
--------
前端源码放在 frontend/，Python 后端源码放在 backend/factor_matrix/，从目录名即可区分职责。
前后端的启动入口、包配置和依赖锁文件保留在仓库根目录，日常命令也在根目录执行。
数据、报告及历史产物保留原路径，通过 Git 忽略规则和独立实验工作目录与源码分开管理。
源码路径及相关配置的变化可能改变新运行的哈希标识；历史审计记录不回写，复现时使用对应代码版本。

上传 GitHub 的目录
------------------
.github/workflows/              GitHub Actions：锁定依赖安装、源码检查、合成测试、前端构建。
config/                        版本化的模型、研究协议、参数、数据政策和审计绑定 JSON。
                               其中引用的本地数据和 Markdown 证据不随仓库上传。
docs/                          项目结构、使用及协作说明；本轮仅上传非 Markdown 文本。
ops/                           运维配置模板；实际安装使用的机器专属 .plist 留在本地。
public/                        前端静态资源入口；demo-backtest/ 下的生成物不上传。
scripts/                       环境初始化、开发启动、数据检查、维护及旧任务兼容入口。
                               新业务计算进入后端 service；脚本不串联其他业务脚本。
frontend/                      React / TypeScript 前端，只展示和交互，不重算研究结论。
  components/                  页面与共享 UI。
    pages/                     数据管道、因子及研究页面。
    backtest/                  账户曲线、成交与风险/合成路径展示。
    workbench/                 研究工作台、侧栏、布局与组件。
      locked/                  锁定布局视图。
      widgets/                 工作台卡片与数据展示。
  config/                      前端导航、管道和工作台配置。
  features/                    按研究、评分领域拆分的前端状态和逻辑。
    research/                  研究界面相关逻辑。
    scoring/                   评分界面相关逻辑。
backend/factor_matrix/          Python 后端包；cli.py / cli_parser.py 提供正式命令入口。
                               根模块负责数据接入、标准化、存储、质量、版本读取与 API。
  calculation/                 正式计算与编排。
    core/                      执行器、端口、插件和层间契约。
    artifacts/                 工件引用、元数据及目录契约。
    components/                数据域、风险、信号、组合、执行等计算组件。
    l1/                        风险暴露、描述子、历史构造与投影。
    l2/                        收益分解、风险估计、研究评估与 G3/G4 诊断。
    publishing/                工件发布和 CURRENT 指针的校验逻辑。
    services/                  业务流程唯一实现，包括账本、回测、研究及独立诊断。
  diagnostics/                 数据覆盖、上市窗口和历史差异等诊断。
  factor_engine/               因子插件契约、发现、注册表和存储。
    diagnostics/               因子诊断命名空间（空目录不会单独进入 Git）。
    plugins/risk/              风险候选因子实现。
  risk_model/                  风险模型配置与契约。
  scoring/                     评分命名空间（当前为空）。
tests/                         Python 单元/合成工程测试与前端曲线几何测试。
                               临时输入在测试临时目录生成，不依赖真实市场数据库。
experiments/                    独立研究分支上的实验说明与执行边界；main 可无此目录。
  fracdiff-v1/                  分数差分 R0 工作区契约，实际输入绑定另在本地登记。

根目录文件
----------
README.md                      仓库入口与安装、验证说明。
pyproject.toml / uv.lock        Python 包配置和主环境依赖锁。
requirements-dev.lock          已有开发依赖锁；标准安装以 uv.lock 为准。
package.json / package-lock.json 前端依赖和 npm 命令。
.python-version / .node-version 固定语言运行时版本。
index.html / vite.config.ts / tsconfig.json 前端入口、打包及类型检查配置。
.env.example                   数据源环境变量示例，不包含真实凭据。
.gitignore                     明确的上传排除规则。

实验分支工作流
--------------
1. main 保存此次代码基线；research/fracdiff-v1 从该基线分出。
2. 在独立 worktree 工作，原目录继续停留在 main；不要同时修改同一个工作目录。
3. worktree 用自己的 .venv / .uv-cache / data / reports。
4. 先完成数据更新与质量门，再将 manifest、版本和实际工件哈希固定为输入。
   只读快照或独立副本可共享；不要把原项目可写 data/ 软链接到实验 data/。
5. R0 截止 2025-02-28，保留固定 d 网格、252 点窗口、训练/验证划分与合成 seed。
6. 每次运行登记代码提交和未提交改动状态、依赖锁、批准与方案哈希、支持集哈希。
7. 实验产物保留在分支工作区本地；通用实现和测试经审阅后才合并 main。

验证与发布门
------------
GitHub CI 使用 -m "not local_data" 执行工程测试，保留 G3 gate 合成正反案例。
local_data 标记隔离真实本地证据、权重工件哈希和六风格批准证据检查；普通 pytest 不过滤它们。
在原数据工作区运行 uv run --locked --extra dev python -m pytest -q -m local_data
可单独执行这三项；缺少工件或哈希不符仍然失败。
真实 G3 发布门仍在具有完整本地证据的环境中执行：
  uv run --locked python scripts/check_g3_release_gate.py
不因源码仓库不含 data/ 而将真实发布门降级为通过。
